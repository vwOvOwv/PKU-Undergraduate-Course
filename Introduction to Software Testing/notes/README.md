## 基本概念

- 软件测试定义：执行程序或系统以发现故障的过程

- PIE 模型：程序错误可被发现的三个必要条件
  - 执行（execution）：错误位置被执行
  - 感染（infection）：错误导致程序状态出现错误
  - 传播（propagation）：错误的程序状态传播，产生可观测的错误结果（例如错误输出）

## 测试生成

### 基于需求的测试生成

- 等价类划分：简单划分和复杂划分

- 边界值分析
  - 基于简单划分
  - 一般取 `b - 1, b, b + 1` ， `b` 为边界值
  - 不能简单拼接边界值，需要适当组合

- 类别划分法
  - 输入功能规范（需求），输出测试规范
  - 过程：分析功能规范、确定类别、划分类别、确定约束条件、编写测试规范（、评估测试规范、导出测试框架、编写测试用例）
  - 优化基于测试规范进行

- 因果图分析
  - 用符号表示原因和结果，以及原因和原因间的逻辑关系
  - 本质上是画真值表，形成状态表，每一列都是一个测试用例

### 基于模型的测试生成

- 对系统设计进行建模，例如用 FSM，用该模型产生测试用例（预期输出由模型给出）

- 不可能检出所有实现的所有可能错误，因此引入故障模型，限制测试关注的故障类型

### 基于代码的测试生成

- 模糊/随机测试生成
  - 可用于检测程序可靠性
  - 问题：测试输入分布可能和实际输入分布不一致，从而导致一些错误可能难以被检出

- 基于结构性覆盖的测试生成
  - 各种覆盖率

- 基于符号执行的测试生成
  - 分析出所有可能的执行路径，对每个路径反推输入应满足的条件，从而构造出对应测试
  - 问题：路径搜索开销大，多约束问题求解难度大

### 基于组合设计的测试生成

- 配置测试
  - 组合输入空间和配置空间形成测试样例
  - 问题：易导致组合爆炸，一般需要进行规约

## 测试充分性准测

`基本块划分 -> 控制流/数据流图 -> 覆盖率计算`
- 基本块入口点：首指令、跳转指令的下一条指令、跳转目标

- $\mathrm{coverage} = |\mathrm{covered}| / (|\mathrm{all}| - |\mathrm{invalid}|)$

### 基于控制流的测试充分性准则

- 语句覆盖 

- 块覆盖

- 判定覆盖：看整个条件判定语句（例如 `if, while`）的真值

- 条件覆盖：看简单条件（例如 `x <= y`）的真值

- 其他覆盖
  - 条件-判定覆盖：两个拼一起
  - 多重条件覆盖：考虑简单条件的所有组合情况
  - 简化的条件-判定覆盖：用真值表规约条件组合，让每个简单条件独立影响结果，从而缩小测试集合

### 基于数据流的测试充分性准则

- def-use, def-clear, c-use, p-use, all-use, dcu, dpu, $CU$, $PU$
  - 注意 p-use 是分支的边集合

- 分析步骤
  - 基本块划分
  - 画数据流图
  - 找每个基本块的 def 和 c-use/p-use
  - 对每个变量的每个 def，记录对应的 c-use/p-use
  - 对每个测试，分析覆盖的 c-use/p-use
  - 分析无效的 c-use/p-use
  - 计算覆盖率


### 基于程序变异的测试充分性准则

- 程序变异：引入一些小的代码变更

- 变异算子
  - 理想变异算子：可找到一组极小的测试，只要这组测试能检出这组变异算子导出的所有变异体，即可说明程序对需求是充分的
  - 期望变异算子：不要求测试极小

- 前提假设
  - 称职程序员假设：程序中的错误数量和规模小
  - 耦合效应：可检出简单错误的测试也能检出复杂错误

- 等价变异体和活跃变异体
  - 等价：在任何输入下变异体和源程序行为一致
  - 活跃：在任何测试输入下变异体和源程序行为一致

- $\mathrm{score} = |\mathrm{killed}| / (|\mathrm{all}| - |\mathrm{equivalent}|)$

- 测试能检出变异体的条件：PIE 模型

## 测试预言

### 规约式预言

从形式化的需求中得到预言

- 基于规约的预言
  - 基于数学模型：建模变量、操作、操作的前置条件和后置条件（影响）
  - 基于状态转换（例如 FSM）
  - 基于历史：用时序逻辑表示事件发生的时刻和顺序

- 断言
  - 仅要求程序在特定位置具有特定性质

- 契约
  - 调用者需满足前置条件才能调用服务，被调用者的输出需满足后置条件才能返回结果给调用者
  - 条件可由过程不变量给出，其在调用过程中可变，但在调用前后需一致

- 基于代数化需求的预言
  - 用一阶逻辑公理化系统的逻辑和行为，从而推导出输入的预期结果

难点：如何比较抽象的测试预言和实际的输出结果

### 派生式预言

从其他非形式化的来源（间接）得到预言

- 伪预言和 N-版本编程
  - 对同一需求写多个版本的程序，相互验证

- 蜕变条件
  - 程序应满足的一些重要属性（e.g., $\sin x = \sin (x + 2\pi)$）

- 回归测试套件
  - 从历史版本的测试中得到新测试

- 系统执行
  - 逆向工程，从大量执行中分析程序属性，对程序建模

- 文本化文档

### 隐式预言

一些现象本身即可说明程序有 bug（例如程序崩溃）

## 回归测试

- 过程和意义
  - 测试用例选择：新版本下部分测试过时，其余测试根据测试对象可分为可复用的测试（测试的是新版本未修改的部分）和需重测的测试（测试的是新版本修改了的部分），因此要重测试集合中剔除掉过时的测试
  - 测试用例化简：可复用的测试和需重测的测试在代码逻辑更新后可能存在一定重叠（冗余），从而可以剔除冗余测试以最小化测试集合，降低测试开销
  - 测试用例排序：也是为了降低测试开销，优先测一些重要的测试

### 测试用例化简

- 转换为带约束的整数线性规划问题
  - 优化目标：最小化测试数量
  - 约束：置信度为 c% 下测试集合的揭错率损失不超过 l%，且测试覆盖所有需求（充分）

### 测试用例排序

需要设计一些指标（基于结构覆盖/变异/测试相似度/需求）度量测试的重要性

- 贪心：覆盖多的优先/覆盖未覆盖部分多的优先

- 搜索：路径搜索/遗传算法
  - 状态：测试集合的某一种置换

- 多目标测试排序
  - 本质是多目标优化问题

- 自适应随机测试排序
  - 每次加入和已优先测试距离最远的测试

- 机器学习排序
  - 转换为多分类问题
  - 输入：测试样例
  - 特征：测试的有关信息（覆盖率等）
  - 输出 & 标签：测试优先级

## 其他内容

### 故障定位

- 基于频谱的故障定位
  - 前提假设：失败测试覆盖的程序元素更容易出错
  - 过程：统计分析失败测试覆盖的程序元素，出现频率越高的越可能是故障所在位置

- 基于变异的故障定位
  - 前提假设：变异正确语句/变异错误语句对原先通过/失败测试的影响不同
  - 过程：产生大量变异，分析原先通过/失败测试的输出变化情况
  - 优势：相比频谱方法更多地捕获了测试和语句之间的具体关系

- 基于程序切片的故障定位
  - 静态切片/动态切片
  - 后向切片（原因）/前向切片（影响）

### 编译器测试

`测试程序构建 -> 测试预言构建 -> 测试化简和排序 -> 执行测试 -> 分析结果`

存在的挑战
- 高效生成用于不同测试目的的测试程序
- 测试预言如何产生（多用伪预言/蜕变测试）
- 测试化简排序的效果和其计算开销之间的权衡
